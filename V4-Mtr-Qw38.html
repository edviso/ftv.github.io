Proyecto B-612 · Micro-modelo v4 · Generalización

📋 El Proyecto

Objetivo: Construir un micro-modelo de inteligencia artificial que no solo memorice respuestas sobre El Principito, sino que comprenda las preguntas y generalice a formulaciones nunca antes vistas.

Problema detectado en v3: La versión anterior aprendió a asociar palabras clave (ej: "zorro" → "amigo") sin entender la estructura lógica. Un simple buscador de texto (TF-IDF) podía superar sus pruebas.

Áreas de conocimiento (fijas):

  • Identidad (Soy el Principito)
  • Vivienda (Planeta pequeño)
  • Rosa (Única)
  • Amistad (Zorro)
  • Nostalgia (Extrañar)
  • Volcanes (Dormidos)
  • Fuera de dominio (Rechazo)

⚙️ Fases del Proyecto

Fase 1 · Ingeniería del Dataset

El cimiento semántico

Teoría

Un modelo solo generaliza si los datos de entrenamiento cubren el espacio de variaciones posibles. En v3, el dataset tenía 81 ejemplos con contradicciones internas que enseñaban relaciones erróneas (ej: "mundo pequeño" → volcanes, pero "planeta pequeño" → vivienda).

Para v4, construimos un grafo de conocimiento con entidades y atributos, y generamos preguntas contrastivas que obligan al modelo a entender la intención, no solo buscar palabras.

Principio clave: Por cada pregunta positiva, debe existir al menos una pregunta adversaria que contenga las mismas palabras clave pero apunte a un tema diferente.

Procedimiento

  1. Definir ontología: 5 entidades × 5 atributos + 1 clase de rechazo.
  2. Crear 50 plantillas gramaticales por cada tema (interrogativas, afirmativas, negativas).
  3. Generar 2,000 pares pregunta→intención usando las plantillas.
  4. Incluir 30% de ejemplos con distractores léxicos de otros temas.
  5. Tokenizar con SentencePiece (vocabulario ~500 subpalabras).
  6. Validar que ninguna pregunta del set de test aparezca en entrenamiento.

Fase 2 · Arquitectura del Modelo

Micro-Transformer con Atención

Teoría

Las redes recurrentes (GRU/LSTM) procesan el texto secuencialmente, lo que dificulta capturar relaciones entre palabras distantes. Los Transformers usan mecanismos de atención que permiten a cada palabra "mirar" a todas las demás simultáneamente.

Para este micro-proyecto, un Transformer de 2 capas con ~350K parámetros es suficiente para aprender composicionalidad sin necesidad de gran poder computacional.

Decisión de diseño: Usamos un Encoder-Only (tipo BERT diminuto) para clasificar la intención en 7 categorías, en lugar de generar texto libremente. Esto elimina alucinaciones y garantiza respuestas canónicas exactas.

Especificaciones

  • Embedding: 500 tokens × 64 dimensiones
  • Capas: 2 bloques Transformer (4 heads, dim=64)
  • Clasificador: Capa densa 64 → 7 clases
  • Parámetros totales: ~350,000
  • Salida: Probabilidad por tema → plantilla de respuesta fija
  1. Implementar tokenizador SentencePiece entrenado en el corpus de 2,000 preguntas.
  2. Construir el Encoder con PyTorch o TensorFlow Lite.
  3. Agregar capa de clasificación con softmax.
  4. Mapear cada clase a su respuesta canónica de v3.
  5. Verificar que el modelo quepa en <5MB para uso en móvil.

Fase 3 · Estrategia de Entrenamiento

Currículum y Regularización

Teoría

El sobreajuste (memorización) ocurre cuando el modelo tiene capacidad suficiente para recordar cada ejemplo de entrenamiento en lugar de aprender patrones generales. Para combatirlo, usamos tres técnicas:

  • Aprendizaje por Currículum: Presentar ejemplos de menor a mayor dificultad.
  • Dropout: Apagar neuronas aleatoriamente durante el entrenamiento para forzar redundancia.
  • Label Smoothing: Evitar que el modelo esté 100% seguro de sus predicciones, mejorando calibración.
Regla de oro: La pérdida de validación debe bajar de forma consistente. Si la pérdida de entrenamiento baja pero la de validación sube, hay memorización → detener entrenamiento.

Procedimiento

  1. Épocas 1-10: Solo preguntas directas sin distractores (aprendizaje base).
  2. Épocas 11-20: Introducir sinónimos y reformulaciones.
  3. Épocas 21-30: Añadir preguntas con distractores y negaciones.
  4. Usar AdamW con learning rate 0.001 y decaimiento lineal.
  5. Dropout de 0.2 en capas de atención y feed-forward.
  6. Early Stopping con paciencia de 5 épocas sobre validación.
  7. Guardar checkpoint solo si mejora en set de validación composicional.

Fase 4 · Batería de Evaluación

Pruebas "Rompe-TF-IDF"

Teoría

En v3, un simple buscador de similitud léxica (TF-IDF) podía resolver el examen porque las preguntas de prueba compartían palabras con el entrenamiento. Para demostrar generalización real, el examen debe contener preguntas que compartan vocabulario pero difieran en estructura lógica.

Tipos de Prueba

  • Test de Inversión de Rol: "¿Soy yo tu amigo?" vs "¿Eres tú mi amigo?" (mismas palabras, distinta relación).
  • Test del Caballo de Troya: "Sé que tienes un zorro, pero ¿cómo son tus volcanes?" (distractor + pregunta real).
  • Test de Negación: "¿Tu rosa NO es única?" (debe seguir reconociendo el tema Rosa).
  • Test de Frontera: "¿De qué color es tu coche?" (debe activar rechazo de dominio).
  • Test de Permutación Extrema: "¿Amigo zorro tu es?" (desorden gramatical, misma intención).
Criterio de éxito: El modelo debe superar el 85% en todas las categorías. Un baseline TF-IDF debe obtener menos del 40% en las mismas pruebas.
  1. Diseñar 300 preguntas de test distribuidas en los 5 tipos anteriores.
  2. Validar manualmente que ninguna pregunta sea ambigua.
  3. Ejecutar baseline TF-IDF sobre el test (debe fallar).
  4. Ejecutar el modelo entrenado y registrar precisión por categoría.
  5. Analizar errores: ¿son fallos de comprensión o de vocabulario?

Fase 5 · Gobernanza y Control

MLOps y Reproducibilidad

Teoría

Un experimento científico solo es válido si es reproducible y si no hay fuga de información entre entrenamiento y evaluación. En v3, el examen sellado tenía sus frases visibles en el código, comprometiendo la validez del resultado.

Controles Obligatorios

  • Sellado criptográfico: El archivo de test se guarda con hash SHA-256 y no se lee durante el entrenamiento.
  • Versionado de datos: Cada dataset tiene un identificador único. Cualquier cambio requiere nueva versión.
  • Configuración inmutable: Hiperparámetros fijados en archivo YAML antes de iniciar. Prohibido ajustarlos manualmente para "mejorar" resultados.
  • Registro automático: Cada ejecución guarda: fecha, hash de código, métricas, y ruta del checkpoint.
  • Auditoría de semillas: Todas las semillas aleatorias se documentan. El experimento debe dar el mismo resultado al repetirse.
  1. Crear repositorio con estructura: /datos, /src, /checkpoints, /test-sellado.
  2. Generar hash SHA-256 del archivo de test antes de entrenar.
  3. Configurar script de entrenamiento para que NO tenga acceso a /test-sellado.
  4. Usar MLflow o archivo JSON para loggear cada época.
  5. Al finalizar, verificar que el hash del test no cambió.
  6. Publicar informe con todos los artefactos y semillas.
